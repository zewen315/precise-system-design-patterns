# Filesystem

## What Is a File?

- Everything is a file (or file-like) in Unix: regular files, directories, devices, sockets, pipes.
- A file's real identity is its inode, not its name — a filename is just a directory entry (a link) that points at an inode.

## Inodes

- What does an inode store (size, permissions, owner, timestamps, pointers to data blocks) — and what does it *not* store (the filename)?
- `stat file.txt`, `ls -i` — inspect a file's inode.
- Why can `df -h` show free space while `df -i` shows the filesystem is out of inodes (many tiny files can exhaust inodes before they exhaust blocks)?

## Hard Links vs Symbolic Links

- A hard link is a second directory entry pointing at the same inode — indistinguishable from the "original" (same inode number, same data, link count > 1).
- A symlink is a small separate file that stores a path string, resolved by the kernel at access time.
- Why can't a hard link cross filesystems, while a symlink can?
- Why doesn't deleting the "original" file break a hard link (the data is only freed once the link count hits zero), but it does break a symlink (a dangling reference)?
- `ln file.txt hardlink.txt` vs `ln -s file.txt symlink.txt`

## File Types

| Symbol | Type |
|---|---|
| `-` | regular file |
| `d` | directory |
| `l` | symlink |
| `b` | block device |
| `c` | character device |
| `s` | socket |
| `p` | named pipe (FIFO) |

- `ls -l`'s first column shows the type; `file <path>` inspects the content to guess a type.

## Virtual File System (VFS)

- What problem does the VFS abstraction layer solve — a single, uniform interface (`open`/`read`/`write`/`close`) over many different filesystem implementations?
- How does the VFS let ext4, XFS, NFS, tmpfs, and `/proc` all look identical to a userspace program?
- `/proc` and `/sys` are virtual filesystems — they don't exist on disk, they're generated by the kernel on read. Why is that a convenient interface for exposing kernel/process state?

## Mounting

- What does "mounting" mean — attaching a filesystem's tree onto a directory (the mount point) of the existing tree?
- `mount`, `umount`, `/etc/fstab` (filesystems mounted automatically at boot).
- `lsblk`, `findmnt`, `df -h` — see what's mounted where.
- What is a bind mount, and why do containers rely on it heavily to expose host paths inside a container's filesystem?
- Why can't you unmount a filesystem that's "busy" (open file handles), and how do you find what's holding it open (`fuser`, `lsof` — see `tools/disk.md`)?

## Filesystem Types

- ext4 — the traditional Linux default; a journaling filesystem.
- XFS — high-performance, common for large files and databases.
- Btrfs / ZFS — copy-on-write, with built-in snapshots and checksumming.
- tmpfs — RAM-backed, disappears on reboot (used for `/tmp`, `/run`).
- What is journaling, and how does it protect a filesystem from corruption on an unclean shutdown (a write-ahead log for metadata — the same idea as a database WAL, see `components/postgres.md`)?

## Disk vs Partition vs Filesystem

- A disk (block device) can be split into partitions; each partition typically holds one filesystem.
- `lsblk`, `fdisk -l`, `parted -l` — inspect disks and partitions.
- LVM (Logical Volume Manager) — why add a layer between partitions and filesystems (resize volumes without repartitioning, snapshots, spanning multiple physical disks)?

## Interview / Practical Usage

- "Disk is full" but `df -h` shows space free — what do you check next (inode exhaustion, a deleted-but-still-open file holding space)?
- How would you quickly find what's eating disk space (`du -h --max-depth=1`, `ncdu`)?
- A process still has a deleted file open — why does `df` keep showing that space as used, and how do you reclaim it without restarting the process (truncate via `/proc/<pid>/fd/<fd>`)?
